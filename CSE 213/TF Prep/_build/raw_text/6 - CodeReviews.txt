===== page 16 =====
Be sure that authors annotate source code 
before the review begins. 
• Annotations guide the reviewer through the changes 
 
• Showing which files to look at first and defending the reason behind 
each code modification. 
 
• Annotations should be directed at other reviewers to ease the 
process and provide more depth in context. 
16 
Source: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/

===== page 17 =====
Establish quantifiable goals for code review and 
capture metrics so you can improve your processes. 
• Set a few tangible goals 
ꟷreduce support calls by 15%, 
ꟷcut the percentage of defects injected by development in half. 
 
• Collect process metrics 
ꟷInspection rate: the speed with which a review is performed 
ꟷDefect rate: the number of bugs found per hour of review 
ꟷDefect density: the average number of bugs found per line of code 
 
17 
Source: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/

===== page 18 =====
Use checklists, because they substantially improve 
results for both authors and reviewers. 
• Developers often make the same 
mistakes over and over 
 
• Omissions in particular are the hardest 
defects to find because it´s difficult to 
review something that isn´t there. 
 
• Checklists are the most effective way to 
eliminate frequently made errors and 
to combat the challenges of omission 
finding. 
18 
Source: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/

===== page 19 =====
Verify that the defects are actually fixed. 
• How will the bugs be fixed? 
 
• Many teams do not have a systematic method for fixing the bugs 
they´ve worked so hard to find. 
 
• Reviewers should log bugs, discuss them with the author, and 
approve changes in the code. 
 
19 
Source: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/

===== page 20 =====
Foster a good code review culture in which finding 
defects is viewed positively. 
• Peer review can put strain on interpersonal team relationships.  
 
• It´s difficult to have every piece of work critiqued by peers and to 
have management evaluating and measuring defect density in your 
code. 
 
• It´s extremely important that mangers create a culture of 
collaboration and learning in peer review. 
 
• While it´s easy to see defects as purely negative, each bug is actually 
an opportunity for the team to improve code quality.  
 
• Defects found in peer review are not an acceptable rubric by which to 
evaluate team members.  
20 
Source: https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/
